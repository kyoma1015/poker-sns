## 管理原則
- GitHub Issue / PR / commit を唯一の技術的な進捗根拠とし、口頭報告のみで PASS にしない。
- 4ラインは専用ブランチと担当進捗ファイルを持つ。変更競合時は統括側で調整する。
- Workやチャット間で自動同期されるわけではないため、作業終了時に必ず進捗ファイルを更新する。
- 本番DBの変更、mainへのマージ、本番デプロイ、課金・破壊的操作はオーナー承認が必要。
- テスト用DBと本番DBの区別を必ず確認。テストで本番利用者データを更新しない。
- 認証情報、アクセストークン、個人情報をGitHub Issue/PR/ログへ投稿しない。
- 品質ゲートは CI・レビュー・必要な実機QA のすべてを満たして初めて PASS。CIだけでは実機QA完了ではない。

## 作業ループ
1. 最新のmain、担当ブランチ、PR、CI、プレビューを照合する。
2. 未解決Issueを重大度・依存関係・影響範囲で優先順位付けする。
3. 担当ブランチで最小限の変更を行い、独立したテストを追加する。
4. CI失敗は調査・修正し、結果と未検証事項を記録する。
5. PRを作成し、影響を受ける他ラインと衝突していないか確認する。
6. 承認が必要な変更は停止し、オーナーに短い判断依頼を出す。

## 自動化の限界
このファイルとGitHub ActionsのCIはAI開発エージェントの自動起動を意味しない。継続的なIssue処理には別途実行環境、権限、起動トリガー、費用管理の構築が必要。
