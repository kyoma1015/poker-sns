# Poll-only GitHub Actions backup/restore threat model — 2026-10-22

**Design only; NO-GO for live data.** No secrets created, no production dump, no restore, no production writes, no Vercel or paid service. Do not merge or enable a production-data workflow based solely on this document.

## Feasibility
An ephemeral GitHub-hosted runner can in principle connect read-only to the managed Supabase PostgreSQL 17 database, export a logical backup, restore into a private isolated PostgreSQL 17 instance on the same runner, run integrity checks, and destroy its filesystem at job end. This is **not yet a verified secure or complete disaster-recovery path**. Supabase Free does not provide the paid daily backup guarantee. GitHub-hosted runners are not long-term backup storage.

## Trust boundaries and required design
1. **Workflow trigger**: use a separately reviewed, manual `workflow_dispatch` workflow with environment approval, protected branch, restricted permissions (`contents: read`), and no pull_request_target or untrusted PR code. No scheduled backup, no automatic secret access, no untrusted dependency execution. Never use arbitrary repository code from a PR in the credential-bearing job.
2. **Secrets**: only GitHub environment secrets (not repository-level by default); do not use `service_role` API key for a DB dump. Use a narrowly scoped, audited, read-only database credential capable of the necessary dump; note that dumping RLS-protected/auth/internal schemas may require elevated access and cannot be assumed possible with a truly read-only role. Do not create a credential on production without explicit authorization. Secrets are not inherently safe against a malicious action, compromised dependency, log output, or shell trace. Masking is best-effort.
3. **Network**: restrict inbound access to the ephemeral runner; avoid publishing PostgreSQL container ports. Restrict outbound effects and disable cron, triggers that send notifications, webhooks, email and other external side effects during restore. Validate the connection's SSL and destination identity.
4. **Sensitive artifacts**: never upload raw `roles.sql`, `schema.sql`, `data.sql`, `pg_dump` archives, query outputs containing identities, logs with credentials, or raw DB snapshots. Redact summaries; artifacts may contain only safe PASS/FAIL, test IDs, counts if not sensitive, and schema/extension compatibility diagnostics. Keep artifact retention minimal; deleting an artifact does not retroactively guarantee removal from all logs/caches.
5. **Cleanup**: use an isolated disposable runner; set job timeout; `if: always()` cleanup for files/containers and revoke ephemeral access where supported, but acknowledge crash/cancellation cleanup is best effort. GitHub-hosted runner teardown is not a substitute for encrypted long-term backup.
6. **Restore compatibility**: production PostgreSQL 17.11 with pg_cron 1.6.4, pg_stat_statements 1.11, pgcrypto 1.3, supabase_vault 0.3.1, uuid-ossp 1.1. Plain PostgreSQL 17 image does not necessarily provide Supabase-specific extensions, Auth/Storage schemas or platform-specific roles. Select and pin a compatible image by digest only after isolated synthetic proof.
7. **Data scope**: 7 `storage.objects` metadata records previously observed; database dump does NOT include object bytes. Auth config, Edge Functions, external providers, secrets and Storage bytes require a separate recovery plan. Never claim complete recovery from a DB-only restore.
8. **Free limits**: verify GitHub repository visibility, runner billing eligibility, Actions minute and storage usage in GitHub billing settings before running. Public/private usage and policy differ. No paid runner, larger runner, paid storage, new Supabase project or PITR.
9. **Evidence gate**: first implement a *separate* no-secrets, no-production-network synthetic restore job and demonstrate PG17/extension compatibility and full cleanup. Only after review/approval should an owner provision a credential and approve a separate live-data job. Verify role permissions, data retention, privacy, threat model, disaster-recovery RPO/RTO and incident response. Live backup execution remains prohibited under the current instruction.
10. **Release gate**: no live-data restore evidence, no complete Storage/side-effects parity, and no cutover authorization means **NO-GO** for production poll migration.
